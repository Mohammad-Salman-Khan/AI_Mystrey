# 1. PROJECT VISION

## 1.1 What Is AI Mystery Room?

AI Mystery Room is an AI-powered interactive mystery investigation website.

The user provides a small scenario, story, or situation. Based on that input, the AI generates a complete fictional investigation containing a mystery, multiple suspects, a hidden culprit, and a collection of evidence.

The evidence can include:

- WhatsApp-style conversations.
- Images related to the incident.
- CCTV footage or camera recordings.
- Witness statements.
- Documents and other digital proofs.
- Timelines and other clues.

The user must investigate the available evidence, connect the clues, understand the suspects' motives and alibis, and select the person they believe is responsible.

Once the user submits their answer, the website reveals the actual culprit and explains how the evidence solves the mystery.

**The core idea is simple:**

User Story → AI Creates Investigation → User Examines Evidence → User Identifies Culprit → AI Mystery Revealed.

The website should make users feel like they are solving a real detective case, while clearly identifying all generated cases and evidence as fictional.

## 1.2 Main Objective

Build a complete, functional website where every mystery is generated dynamically from the user's input using Gemini.

The website must not rely on a fixed collection of predefined mysteries as its main functionality. Every new scenario should produce a new investigation.

## 1.3 Core Product Principles

1. The user's scenario determines the mystery.
2. Gemini generates the investigation and its evidence.
3. Every investigation has one intended culprit.
4. Evidence must contain meaningful clues that allow the user to solve the case.
5. The culprit must remain hidden until the user submits an accusation.
6. The application must explain the solution after the investigation.
7. AI-generated media must be genuinely generated by the configured provider or clearly presented as a text-based simulation or placeholder.
8. The interface must be immersive, interactive, and easy to understand.

# 2. COMPLETE USER EXPERIENCE

## Step 1: Enter the Mystery Scenario

The user opens the AI Mystery Room homepage.

The homepage presents a text area where the user can describe a story or situation.

Example:

"A valuable prototype disappeared from a college laboratory during a power cut. Four students had access to the room, and everyone claims they were somewhere else."

The user clicks **Create My Mystery**.

The website sends the scenario to the backend.

## Step 2: AI Generates the Investigation

The backend sends the scenario to Google Gemini.

Gemini creates a complete investigation containing:

- A case title.
- A case description.
- Incident details.
- Suspects.
- Suspect profiles.
- Motives and alibis.
- An incident timeline.
- Evidence artifacts.
- Contradictions and clues.
- Red herrings.
- One culprit.
- A hidden solution.

The backend validates the generated investigation and prepares it for the frontend.

The user sees a loading screen while the investigation is being prepared.

Suggested loading messages:

- Creating your mystery...
- Identifying the suspects...
- Generating evidence...
- Preparing the investigation room...

These messages are interface feedback, not claims that Gemini exposes its internal reasoning.

## Step 3: Enter the Investigation Room

Once generation finishes, the user enters the investigation interface.

The screen presents:

- Case title.
- Case briefing.
- Incident details.
- Suspect list.
- Evidence collection.
- Investigation timeline, when relevant.
- Navigation between investigation sections.

The interface should feel like a detective's investigation workspace.

The user should be able to move between suspects and evidence without losing the case.

## Step 4: Investigate the Suspects

Display the suspects as individual cards.

Each suspect should have:

- Name.
- Profile image or generated portrait, if supported.
- Short background.
- Relationship to the incident.
- Possible motive.
- Alibi.
- Relevant information available to the investigator.

All suspects should initially appear plausible enough to investigate.

Do not mark the culprit or expose the answer.

## Step 5: Examine the Evidence

The user can open and examine every generated evidence item.

### A. WhatsApp Messages

Display fictional chat conversations in a familiar messaging interface.

Each conversation can contain:

- Participant names.
- Message bubbles.
- Timestamps.
- Relevant conversation history.
- Suspicious messages.
- Statements that contradict an alibi.
- Clues that establish relationships or timelines.

Messages should be consistent with the case timeline and suspect identities.

### B. Images

Images should be generated through an actual image-generation provider when image generation is configured.

Examples include:

- A scene where the incident occurred.
- An object found at the scene.
- A suspicious item.
- A photograph that establishes someone's presence.
- An image containing a visual clue.

If an image provider is not configured, the interface may display a descriptive placeholder. It must not pretend that an actual image was generated.

### C. CCTV and Camera Evidence

The intended experience includes camera recordings that help the user investigate.

When a compatible video-generation provider is configured, the system may generate actual fictional clips.

Otherwise, the MVP should support fictional CCTV-style evidence through timestamped event logs, still images, or a camera playback interface clearly identified as simulated.

For example:

18:42 — Person enters the corridor.

18:46 — Corridor lights go out.

18:51 — Person exits carrying a bag.

These events must be consistent with the case timeline.

Do not display fake video files or claim that a recording exists when it does not.

### D. Documents and Other Proofs

The AI may generate additional evidence types, including:

- Witness statements.
- Notes.
- Reports.
- Emails.
- Receipts.
- Access logs.
- Timelines.
- Physical evidence descriptions.

Only include evidence types relevant to the user's scenario.

### Evidence Interaction Requirements

The user must be able to:

- Browse all evidence.
- Open evidence in detail.
- Filter evidence by category.
- Read full evidence content.
- Navigate back to the investigation.
- Compare evidence with suspect statements.

The evidence interface must be usable on mobile and desktop.

## Step 6: Select the Culprit

After investigating the evidence, the user selects the suspect they believe committed the fictional crime or caused the incident.

The website presents a clear action:

**Submit Your Final Accusation**

Before submission, show a confirmation message.

The backend validates the selected suspect and compares the accusation with the hidden solution.

For the MVP, allow one final accusation per case.

## Step 7: Reveal the Mystery

After submission, reveal:

- Whether the user selected the correct culprit.
- The actual culprit's identity.
- The explanation behind the incident.
- The decisive clues.
- How the evidence connects.
- Which suspect statements were misleading.
- Why the other suspects were not responsible.

The result screen should feel satisfying and explain the logic of the mystery.

Provide a **Create Another Mystery** button so the user can immediately begin a new investigation.

# 3. AI GENERATION REQUIREMENTS

## 3.1 Google Gemini Integration

Google Gemini is the primary AI provider.

The backend must call Gemini through a supported server-side SDK or API.

Never call Gemini directly from React or expose the Gemini API key to the browser.

Gemini must generate the investigation dynamically using the user's scenario as its input.

## 3.2 Information Gemini Must Generate

For every investigation, Gemini must create:

1. Case title.
2. Case summary.
3. Incident description.
4. Fictional location and setting.
5. Three to five suspects for a typical short mystery.
6. Suspect identities and profiles.
7. Motives and alibis.
8. An incident timeline.
9. Five to eight evidence items for a short mystery.
10. Multiple meaningful clues.
11. Plausible red herrings.
12. One intended culprit.
13. A complete hidden solution.
14. A logical explanation connecting evidence to the culprit.

The system may support longer investigations later, but a short investigation should be the initial default.

## 3.3 Mystery Quality Rules

Every generated investigation must satisfy the following requirements:

- Exactly one intended culprit.
- The culprit must be one of the generated suspects.
- At least three meaningful clues should contribute to solving the case.
- Evidence must be consistent with the incident timeline.
- Messages and statements must refer to the correct suspects.
- Important contradictions must be logically explainable.
- Red herrings must be misleading without making the mystery impossible.
- The intended solution must be inferable from the available evidence.
- The explanation must reference actual evidence in the case.
- The solution must not contradict decisive evidence.

Gemini output must be validated by the backend before the case becomes playable.

If the output is invalid, the backend should attempt one repair or regeneration before returning a helpful error.

# 4. AI-GENERATED MEDIA ARCHITECTURE

The project must distinguish between text generation, image generation, and video generation.

## 4.1 Text Generation

Gemini generates:

- Case narratives.
- Suspect descriptions.
- WhatsApp-style conversations.
- Witness statements.
- Documents.
- Timelines.
- CCTV event descriptions.
- Clues and solutions.

## 4.2 Image Generation

Actual generated images require an image-generation model or provider that supports image output.

The image-generation integration must be isolated behind a service so the provider can be changed without redesigning the application.

Generated image metadata should include:

- Evidence ID.
- Image URL or storage reference.
- Generation status.
- Relevant description.

If image generation is unavailable, show a clearly labeled placeholder or textual evidence description.

Do not use an unrelated stock image as if it were proof from the generated case.

## 4.3 Video Generation

Actual video recordings require a compatible video-generation provider.

The application must not assume that a text response from Gemini is a video.

If actual video generation is unavailable, support a simulated camera evidence experience containing:

- Camera identifier.
- Timestamped events.
- Observations.
- Optional generated still images.
- A clear indication that the evidence is simulated.

The architecture should allow actual generated video to be added later without changing the core investigation flow.

Use:

- React.

- Loading and error states.
- Case briefing display.
- Suspect cards.
- Evidence browsing.
- Evidence detail views.
- Accusation selection.
- Result and solution display.

## 5.2 Backend

- Node.js.
- Express.js.
- TypeScript.
- Mongoose.
- Zod or an equivalent validation library.

Responsibilities:

- API endpoints.
- Input validation.
- Gemini integration.
- Investigation generation.
- Output validation.
- Image/video provider integration.
- MongoDB persistence.
- Hidden solution management.
- Accusation evaluation.
- Rate limiting.
- Error handling.

## 5.3 Database

Use MongoDB to persist generated investigations.

Each case should contain:

- Unique public case ID.
- Original scenario.
- Case metadata.
- Suspects.
- Evidence.
- Incident timeline.
- Hidden solution.
- Case status.
- Accusation, if submitted.
- Creation and expiration timestamps.

Use a random, unguessable public case ID.

The solution must be stored server-side and excluded from all public case responses.

A default seven-day case retention period is appropriate for the MVP and should be configurable.

# 6. DATA STRUCTURE

Use a structured schema for every generated mystery.

A conceptual case object:

```json
{
  "title": "The Missing Prototype",
  "scenario": "The user's original scenario",
  "briefing": "The fictional incident briefing",
  "setting": "University laboratory",
  "suspects": [
    {
      "id": "suspect_1",
      "name": "Alex Morgan",
      "profile": "Research assistant",
      "motive": "Wanted access to the prototype",
      "alibi": "Claims to have been in the library"
    }
  ],
  "timeline": [
    {
      "time": "18:42",
      "description": "Someone enters the corridor"
    }
  ],
  "evidence": [
    {
      "id": "evidence_1",
      "type": "messages",
      "title": "Recovered Chat",
      "description": "A fictional conversation",
      "content": "Message transcript",
      "relatedSuspectIds": ["suspect_1"]
    }
  ],
  "solution": {
    "culpritSuspectId": "suspect_1",
    "explanation": "The explanation of the incident",
    "decisiveEvidenceIds": ["evidence_1"],
    "redHerringEvidenceIds": []
  }
}
```

This is an illustrative schema. The implementation must validate the complete object and maintain separate internal and public response types.

The public response must not include the `solution` field or any equivalent hidden-answer data.

Evidence types should support:

- `messages`
- `image`
- `video`
- `camera_log`
- `witness_statement`
- `document`
- `physical_clue`

Media records must include a generation status so the frontend can distinguish ready media from pending, failed, or unavailable media.

# 7. API SPECIFICATION

Base path:

`/api/v1`

## POST `/cases`

Creates a new mystery from the user's scenario.

Request:

```json
{
  "scenario": "A valuable prototype disappeared during a power cut.",
  "difficulty": "medium"
}
```

The backend must:

1. Validate the scenario.
2. Call Gemini.
3. Validate the generated investigation.
4. Save the complete case in MongoDB.
5. Return the player-safe case data.

Success response: `201 Created`.

The response must exclude the hidden solution.

## GET `/cases/:caseId`

Returns the saved investigation.

Includes:

- Case title and briefing.
- Suspects.
- Timeline.
- Evidence.
- Media status.
- Case status.

Never return the hidden solution through this endpoint.

Return a suitable error for unknown or expired cases.

## POST `/cases/:caseId/accusation`

Request:

```json
{
  "suspectId": "suspect_1"
}
```

The backend must:

1. Load the case.
2. Validate the selected suspect.
3. Confirm that the case is not already completed.
4. Compare the accusation with the stored culprit.
5. Record the accusation atomically.
6. Return the result and solution explanation.

Return `409 Conflict` if the case already has a final accusation.

## GET `/health`

Returns application and database health without exposing credentials.

## Error Handling

Use a consistent error response:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check your scenario.",
    "requestId": "request-id"
  }
}
```

Do not expose stack traces, API keys, raw provider errors, or internal prompts.

# 8. WEBSITE DESIGN

## 8.1 Visual Direction

Create an immersive detective investigation interface.

The design should feel like a combination of:

- A detective's case file.
- A digital investigation room.
- An evidence management dashboard.
- An interactive mystery game.

Use dark backgrounds, clear typography, evidence cards, subtle highlights, readable timelines, and distinctive evidence-category icons.

Avoid excessive visual effects that interfere with usability.

## 8.2 Homepage

Must include:

- AI Mystery Room logo and name.
- A strong headline.
- Short explanation of how the game works.
- Scenario input area.
- Example scenarios.
- Difficulty selection.
- Create Mystery button.
- Fictional-content notice.

## 8.3 Investigation Dashboard

Must include:

- Case title and briefing.
- Suspect navigation.
- Evidence navigation.
- Timeline.
- Evidence detail area.
- Clear case progress indicators.
- A persistent option to submit the final accusation when the user is ready.

Do not reveal the culprit through the UI.

## 8.4 Evidence Interface

Give different evidence types appropriate layouts:

- Messages should look like a fictional chat interface.
- Images should open in a viewer.
- Videos should have a playback interface only when actual playable media exists.
- Camera logs should display timestamped observations.
- Documents should look like readable case documents.
- Witness statements should have a clear statement format.

## 8.5 Result Screen

Show:

- The user's accusation.
- Correct or incorrect status.
- The actual culprit.
- Explanation of the incident.
- Decisive clues.
- Red herrings.
- A new mystery action.

# 9. SECURITY AND RELIABILITY

Implement the following:

- Environment-based secrets.
- Request validation.
- Rate limiting.
- Server-side accusation evaluation.
- Atomic final accusation submission.
- MongoDB expiration.
- Gemini request timeouts.
- Safe error handling.
- CORS configuration.
- HTTP security headers.
- Safe rendering of AI-generated content.
- Protection against exposing the hidden solution.

All generated names, messages, locations, and investigations must be fictional.

The product must not imply that generated evidence proves wrongdoing by real people.

Do not allow generated HTML or scripts to execute in the browser.

# 11. ERROR AND LOADING STATES

The website must gracefully handle:

- Invalid scenario input.
- Gemini API failure.
- Gemini timeout.
- Invalid AI-generated JSON.
- Inconsistent clues or suspect references.
- Image-generation failure.
- Video-generation unavailability.
- MongoDB connection failure.
- Unknown case.
- Expired case.
- Duplicate accusation.
- Network disconnection.

Display understandable messages to the user and preserve the scenario when retrying case generation.

The user should never see a blank page or raw server error.

# 12. ACCEPTANCE CRITERIA

The MVP is complete when:

1. The user can enter a custom scenario.
2. Gemini dynamically generates a mystery from that scenario.
3. The backend validates the investigation.
4. A case contains suspects, evidence, and one intended culprit.
5. The user can browse all generated evidence.
6. The user can inspect message conversations and camera evidence.
7. Actual images and videos are used only when supported providers generate them.
8. The user can select and submit a culprit.
9. The backend evaluates the accusation.
10. The correct solution remains hidden until submission.
11. The result screen explains the solution using evidence.
12. Cases persist in MongoDB.
13. Errors and loading states are handled.
14. API keys remain secure.
15. The website works on mobile and desktop.
16. Automated tests and production builds pass.
